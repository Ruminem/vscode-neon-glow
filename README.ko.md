# vscode-neon-glow

[English](README.md) · **한국어**

VS Code 구문 강조에 네온 글로우를 입힘 — **테마를 가리지 않고**.

테마를 함께 배포하지 않음. 지금 쓰는 테마가 만들어내는 색을 그대로 읽어서 그중 선명한
것만 빛나게 하므로, 테마를 계속 바꿔도 글로우가 따라옴. 리로드도 필요 없음.

## 어떤 토큰이 빛나는가

세기는 HSL 채도가 아니라 **크로마**(`max(r,g,b) - min(r,g,b)`)로 결정됨.
이 구분이 중요함. HSL 채도는 `1 - |2L-1|`로 나누기 때문에 흰색에 가까운 색에서 값이 폭발함.
Monokai의 기본 텍스트 `#F8F8F2`는 실제 색 퍼짐이 `0.024`밖에 안 되는데 HSL 채도로는 `0.31`이
나옴 — 채도 임계값을 슬쩍 통과해서 *본문 텍스트*까지 빛나게 만들기에 충분한 값임.
크로마에는 그런 실패 양상이 없음.

Monokai에서 측정한 값:

| 색상      | 역할            | 크로마 | 세기 |
|-----------|-----------------|--------|----------|
| `#F92672` | 키워드          | 0.827  | 1.00     |
| `#FD971F` | 매개변수        | 0.871  | 1.00     |
| `#A6E22E` | 함수 이름       | 0.706  | 0.89     |
| `#66D9EF` | 타입 / 클래스   | 0.537  | 0.68     |
| `#AE81FF` | 숫자            | 0.494  | 0.63     |
| `#E6DB74` | 문자열          | 0.447  | 0.58     |
| `#F8F8F2` | 일반 텍스트     | 0.024  | — (건너뜀) |
| `#88846F` | 주석            | 0.098  | — (건너뜀) |

색에서 역할을 역추론하는 방식이라, 서로 다른 역할에 같은 색을 재사용하는 테마는 구분하지
못함. 역할별로 색이 뚜렷이 나뉘는 테마(Monokai, Tokyo Night, Dracula, …)에서 잘 동작함.

괄호 쌍 색상은 VS Code에 맡김. 저쪽은 `.monaco-editor .bracket-highlighting-N`으로 칠하는데,
토큰 스타일시트를 이루는 단일 클래스 `.mtkN`보다 클래스가 하나 더 많음. 그래서 글로우가 색에
`!important`를 붙이면 특이도를 무시하고 이겨서 모든 중첩 단계가 한 색으로 뭉침. 글로우는 색에
`!important`를 붙이지 않고, 괄호에는 `currentColor`로 된 규칙을 따로 줌. 그래서 각 단계가
실제로 칠해진 그 색으로 빛남.

## 토큰 말고 빛나는 것

토큰 글로우는 항상 켜져 있음. 나머지 일곱 개는 아님 — 전부 꺼진 채로 나가고, 설정에서
값을 넣기 전까지는 아무 일도 일어나지 않음. 칠하는 방식만이 아니라 에디터가 하는 일을
바꾸는 것들이라 그렇게 해뒀음.

**찾기 결과와 선택 영역**(`findGlow`, `selectionGlow`)은 토큰 글로우와 같은 생각을 두
표면에 더 적용한 것임. 색은 여전히 테마에서 오고 여기서 정하지 않음. 그중 찾기 결과는
글로우가 장식이 아니라 실제로 일을 하는 유일한 자리임 — 스크롤바의 표시를 뒤지지 않아도
매치가 어디 있는지 보임.

두 색은 글자 뒤에 깔리는 색이라 테마가 반투명으로 잡아둠. 그래서 블러만 시키면 거의
보이지 않음. 이 둘에만 `spread`가 붙어 있는 이유임 — 블러에 두 가지 일을 시키는 대신,
약한 색을 원래 폭만큼 먼저 밀어낸 다음에 번지게 함. 커서 색은 불투명이라 스프레드가
필요 없음. 규칙이 서로 다르게 생긴 것은 그 때문임.

**커서가 놓인 심볼**(`occurrenceGlow`)은 그 심볼이 화면에 나온 자리를 전부 밝힘. 색은
테마가 이미 그 하이라이트에 주는 색임. 찾기 바로 옆 표면에 같은 유도를 한 번 더 적용한
것이고, `spread`가 붙는 이유도 찾기 규칙과 같음.

그림자는 한 겹만 씀 — 찾기는 두 겹임. 시작 값도 더 낮음, `18` 대신 `10`임. 둘의 차이는
어떻게 보이느냐가 아니라 언제 존재하느냐임. 찾기 결과는 뭔가를 찾는 동안에만 화면에
있지만, 이쪽은 커서가 단어에 놓일 때마다 나타나서 커서가 거기 머무는 내내 남아 있음 —
하루의 대부분임. 항상 돌아가는 규칙이 싼 쪽이어야 함. 테마가 읽기와 쓰기를 다른 색으로
칠하는 경우에는 쓰기를 더 넓게 밝힘. 그 구분은 테마가 한 것이고 따라가는 데 드는 비용이
없음. 언어 서버가 답하지 않을 때 VS Code가 대신 쓰는 텍스트 매치도 같이 밝히므로, 아무도
이해하지 못하는 파일에서도 효과가 살아 있음. 전부 VS Code 자신의
`editor.occurrencesHighlight`가 켜져 있어야 돌아가는데, 끄지 않았다면 켜져 있음.

**거터의 변경 막대**(`gutterGlow`)는 테마 자신의 `editorGutter` 색으로 빛남. 소스 관리가
남기는 추가·수정·삭제 표시고, 원래 거터에서 색을 지닌 유일한 자리임.

이건 블러가 아니라 `spread`가 끌고 감. 찾기와 이유가 다름. VS Code는 이 막대를 요소
자신의 왼쪽 테두리로 그리는데 **스타일만 주고 폭을 안 줌.** 그래서 CSS 초기값인
`medium`, 곧 3px이 그대로 폭이 됨. 글로우를 거는 상자는 그 요소의 `:before`인데 이쪽은
`width: 0`임. **넓이가 없는 상자의 그림자는 블러를 아무리 키워도 아무것도 안 그림.**
그래서 여기서는 spread가 빛에 몸을 주는 것 자체를 맡음 — 찾기는 색이 약해서 spread가
필요했고, 이쪽은 상자가 비어서 필요함. 숫자를 올리면 부드러워지기보다 넓어짐.

삭제 표시는 막대가 아니라 쐐기로, 다른 의사 요소에 그려짐. 그래서 그쪽에 따로 붙였음.
종류마다 규칙이 둘씩임 — 하나는 그냥, 하나는 `.secondary`. VS Code가 자기가 하지 않은
변경을 위해 거터 색을 한 벌 더 만들었는데, 그게 없는 빌드에서 걸리는 것이 그냥 쪽임.

비용은 여기 있는 어느 효과보다 좁게 묶임. 뷰포트가 아니라 **마지막 커밋 이후 고친 줄
수**에 묶이고, 그나마 소스 관리 아래 있는 파일에서만 나옴.

**커서 잔상**(`cursorTrail`)은 커서가 튀는 대신 새 위치까지 건너갈 시간을 줌. 커서에
이미 걸려 있는 글로우가 그동안 끌려서 짧은 꼬리로 남음. 움직임만 바꾸는 것이고 색은
테마 것 그대로임. 키를 칠 때마다 트랜지션이 다시 시작되므로 시간이 길면 커서가 지금
치고 있는 글자보다 뒤에 처짐 — `130`은 렉처럼 읽히고, `45`는 타이핑을 따라가면서도
파일을 가로질러 뛸 때는 꼬리가 남음. VS Code에도 `editor.cursorSmoothCaretAnimation`이
있는데 80ms 고정임. 둘 다 켜면 여기 값이 이김.

같은 값이라도 화면 주사율에 따라 다르게 읽힘. 60Hz에서 `45`는 세 프레임이 안 되므로
미끄러지는 대신 한두 번 끊겨 보이고, 144Hz에서는 같은 값이 예닐곱 프레임임 — 주사율이
낮으면 올려 잡는 쪽이 맞음. 게다가 여기서 움직이는 것은 `left`와 `top`이라 슬라이드하는
동안 프레임마다 메인 스레드가 풀어야 함. 프레임 자체도 싸지 않음.

**저장 시 흔들림**(`saveShake`)은 파일을 저장할 때 워크벤치를 옆으로 한 번 침. 인라인
스타일을 쓰는 루프가 아니라 `transform`만 건드리는 CSS 애니메이션이라, 일단 시작하면
프레임이 메인 스레드에 아무것도 요구하지 않음. 주장은 거기까지임 — 어느 쪽이 아래 깔린
글로우를 다시 그리는지는 재본 적이 없음. 넷 중 이것만 아무 데서도 유도되지 않음.
장식이고, 원하지 않으면 꺼져 있음.

**커서 아크**(`caretArc`)는 커서가 방금 지나간 길을 따라 빛을 그림. 여기서 유일하게
숫자가 아니라 **고르는** 설정임 — `arc`는 지나온 길을 밝히며 달리는 꺾인 번개,
`beam`은 같은 것을 직선으로, `comet`은 뒤에 아무것도 안 남기고 날아가는 짧은 머리,
`flash`는 커서가 도착한 자리에서 터지는 섬광임. 커서를 움직이는 것이면 무엇이든 발동함
— 키, 클릭, 다음 찾기, 정의로 이동.

`caretArcMinJump`는 **얼마나 작은 움직임까지 이동으로 칠지**를 정함. 기본값 `5`는 한
글자보다 작아서 화살표 한 번에도 걸림. 화살표를 꾹 누르면 커서를 따라 빛이 함께 달리는
것처럼 보이는데, 이 기능이 노리는 그림이 그거임. 동시에 **이 기능에서 비용이 드는 유일한
자리**이기도 함 — 키를 누르고 있으면 반복마다 하나씩 그림. 거슬리면 올리는 게 그 레버임.
`40`이면 진짜 도약만 걸림: End, `Ctrl+←→`, 멀리 클릭.

앞의 셋은 여전히 그릴 자리가 있어야 함. Tab은 커서를 두 글자쯤 옮기는데, 폭 14px짜리
번개는 번개라기 어려움. **그 크기에서 읽히는 건 `flash` 하나임** — 여정이 아니라 도착을
표시하니까.

이것들은 스타일시트가 아니라 SVG로 만들어짐. 그런데 워크벤치가 Trusted Types를
강제해서 `innerHTML`에 대입하면 예외가 남 — 그래서 모든 노드를 `createElementNS`로
만듦. 그리고 이건 **작업하는 동안 에디터를 지켜보는 첫 기능**이기도 함. 포커스된
에디터의 커서 레이어에 MutationObserver를 걸고, 커서의 인라인 `left`/`top`을
문자열로 읽어 비교하므로 평범한 타이핑에는 레이아웃 비용이 없음. 실제로 그리는
프레임에서만 사각형을 잼.

움직이는 셋, 그러니까 커서 잔상과 저장 흔들림과 커서 아크는 시스템이 모션 줄이기를
요청하면 빠짐.
저장이라는 사건이 렌더러까지 닿는 길은 토글과 같은 선임 —
[토글이 에디터까지 닿는 경로](#토글이-에디터까지-닿는-경로)에 설명이 있음. 페이로드는
워크벤치 안에 있어서 확장 호스트를 다른 방법으로는 들을 수 없음.

## 켜고 끄기

토글은 진짜 VS Code 명령이라 일반적인 키바인딩 시스템 안에 있음. 명령 팔레트(`F1`)에서:

| 명령 | |
|---------|--|
| `Neon Glow: Toggle` | 글로우를 즉시 뒤집음 |
| `Neon Glow: Enable` / `Neon Glow: Disable` | 명시적으로 지정함 — 실제로 뭔가 바뀌는 쪽만 목록에 나옴 |
| `Neon Glow: Show status` | 현재 상태와, 번들이 패치돼 있는지 |

팔레트는 context key로 `Enable`/`Disable`을 걸러내므로 둘 중 어느 쪽이 지금 유효한지 따질 필요가
없음. 키 할당은 양쪽 다 그대로 됨. `commandPalette`의 `when` 절은 팔레트에서만 숨길 뿐
키바인딩 시스템에서 숨기지 않음.

키는 `neonGlow.on`과 `neonGlow.off` 두 개이고, 둘 다 일부러 긍정형임. `when` 절은 설정되지 않은
키와 false인 키를 구분하지 못함. 그래서 `enabled` 키 하나만 쓰면 리로드부터 확장이 활성화되기
전까지의 구간에서 `!enabled`가 참이 되어, 이미 빛나고 있는 에디터 위에 `Enable`을 내밂. 렌더러는
누구를 기다리지 않고 `localStorage`에서 자기 상태를 복원하기 때문임. 키가 둘이면 그 구간이
*아직 모름*으로 읽힘. 어느 것도 목록에 없고, context key가 아니라 상태 파일을 읽는 `Toggle`은
그 사이에도 동작함.

번들을 패치하고 원상복구하는 것은 팔레트에 **없음**. VS Code 자신의 사용/사용 안 함/제거 버튼
옆에 놓이면 "Install"과 "Remove"는 확장 관리로 읽히는데 실제 의미는 전혀 다르고, 그것이 필요한
모든 경로가 이미 필요한 순간에 제안하기 때문임. 패치는 활성화 때의 프롬프트, 상태 표시줄 항목,
`Show status`가 맡고, 원상복구는 번들까지 함께 가져가는 제거 버튼이 맡음. 키 할당은 양쪽 다
그대로 됨.

`Show status`는 번들이 패치를 필요로 할 때만 패치를 제안하고, 아니면 아무 버튼도 내밀지 않음.
그것은 읽는 화면이고, 읽는 화면의 유일한 버튼 자리에 파괴적 동작이 놓일 자리는 없음.

**기본 키바인딩은 일부러 넣지 않았음.** 다른 확장과 충돌하는 것이 원천적으로 불가능해지는
지점이 바로 여기임. *바로 가기 키*(`Ctrl+K Ctrl+S`)에서 `Neon Glow`를 검색해 원하는 조합을
직접 걸면 되고, 이미 점유된 조합이면 VS Code가 알아서 경고해줌.

토글은 설치 디렉터리의 파일을 건드리지 않으므로 관리자 권한도 재시작도 필요 없음.

오른쪽 상태 표시줄에 `NEON:ON` / `NEON:OFF`가 뜨고, 클릭하면 토글됨.
장식이 아님 — 아래를 보라.

스위치는 켜져 있는데 빛날 수가 없는 세 상태도 여기서 알려줌. 에디터에서 보면 셋이 구분되지
않기 때문임. **경고색 배경**은 번들이 패치되지 않았거나, 예전 릴리스의 페이로드를 담고 있거나,
이 창이 뜬 뒤에 패치돼서 렌더러가 아직 부팅 때의 번들을 돌리고 있다는 뜻임. 어느 쪽인지는
툴팁이 말해주고, 클릭하면 그것을 해결하는 동작이 실행됨. 마지막 검사는 일부러 한쪽으로만
판단함. "창 다시 로드"는 확장
호스트만 재시작하고 렌더러는 캐시된 번들에 그대로 두기 때문에, 패치 후 리로드한 창은 확장
쪽에서 보면 멀쩡한 창과 똑같음. 그래서 추측하지 않고 침묵함.

### 토글이 에디터까지 닿는 경로

명령은 확장 호스트에서 돌고 글로우는 렌더러에 있음. 둘 사이에는 API가 없어서, 상태는 두 개의
채널을 동시에 타고 건너감.

**빠른 쪽: 상태 표시줄.** 확장의 상태 표시줄 항목 자체가 전선임. 라벨이 곧 상태이며 평문임
(코디콘을 넣으면 엘리먼트로 렌더돼서 매칭이 깨짐). 렌더러는 **그 항목 하나에**
`MutationObserver`를 걸어둠. 확장 호스트가 그것을 그리는 바로 그 프레임에 토글이 도착하니
대략 16ms임.

상태 표시줄 전체가 아니라 항목에 거는 이유가 있음. 상태 표시줄은 커서가 움직일 때마다 변하므로,
서브트리를 감시하면 타이핑하는 내내 프레임마다 깨어나 모든 항목의 텍스트를 다시 만들고 정규식을
돌리게 됨 — 얻는 것은 아무것도 없이. 우리가 넣은 항목은 글로우를 토글할 때만 바뀜. 몰려오는
레코드는 여전히 `requestAnimationFrame`으로 프레임당 한 번으로 합쳐지고, VS Code가 항목을
교체하면 옵저버도 같이 조용해지므로, 아래의 폴링이 엘리먼트가 끊긴 것을 보고 다시 찾음.

**느린 쪽: 상태 파일.** 확장은 `state.json`을 자신의 `globalStorage`에도 씀. 이 위치는
`vscode-file` 프로토콜 핸들러가 서빙해주는 루트 중 하나라서, 주입된 스크립트가 폴링할 수 있음.

```js
addValidFileRoot(e.appRoot)
addValidFileRoot(e.extensionsPath)
addValidFileRoot(...globalStorageHome...)   // <- 상태 파일이 여기 있음
```

폴링은 빠른 쪽이 놓친 것을 메움. 상태 표시줄을 숨겼거나, `requestAnimationFrame`이 돌지 않는
백그라운드 창인 경우임. 800ms로 돌다가 상태 표시줄 쪽이 동작한다는 게 확인되면 1500ms로
물러남. 그래서 상태 표시줄을 숨겨도 토글이 깨지는 게 아니라 반응이 느려지는 데서 그침.

양쪽 다 *첫* 읽기는 적용하지 않고 기록만 함. 시작 시 상태는 `localStorage`에서 오므로, 오래된
파일이나 아직 쓰이지 않은 상태 표시줄이 마지막으로 알려진 상태를 덮어쓸 수 없고, 부팅 때 엉뚱한
상태가 깜빡이지도 않음.

두 경로가 모두 없으면(확장 없이 CLI로만 패치한 경우 등) 스크립트는 `Ctrl+Alt+N`으로 물러남.
**버블** 단계에 등록되어 있어서 VS Code가 이미 점유한 조합이 언제나 이기고, 그 경우 폴백은 그냥
발동하지 않음. 어느 한쪽이라도 응답하면 폴백은 완전히 물러섬. 조합을 옮기려면
`neon-glow.js`의 `FALLBACK_KEY`를 고치고, 아예 없애려면 `null`로 두면 됨.

끌 때는 엘리먼트를 제거하는 대신 스타일시트의 `disabled` 플래그를 뒤집음. 그래서 다시 켤 때
정규식 패스를 테마 토큰 스타일에 다시 돌리지 않고 이미 파싱된 CSS를 재사용함.

DevTools 콘솔에서 직접 부릴 수도 있음.

```js
__neonGlow.toggle();    // .enable() / .disable() / .isEnabled()
__neonGlow.bridgeOk();  // 둘 중 하나라도 살아있나?   빠른 쪽만 보려면 .statusBarOk()
```

## 설치

VS Code 설치 디렉터리에 쓰기 권한이 필요함. Windows에서는 터미널을 관리자로, macOS/Linux에서는
`sudo`로 실행함.

### 릴리스에서 (권장)

Windows라면 [Releases](https://github.com/Ruminem/vscode-neon-glow/releases)에서
`neon-glow-<version>-windows.zip`을 받아 풀고 `install.cmd`를 더블클릭함. VS Code를 찾고,
확장을 설치하고, 번들을 패치하는 것까지 한 번에 함. 따로 깔아둘 것은 없음. VS Code가
Electron이라 `Code.exe`가 패치 스크립트를 돌릴 Node 노릇까지 겸함.

macOS와 Linux는 `neon-glow-<version>-macos-linux.tar.gz`를 받아 풀고 `./install.sh`를 실행함.
하는 일은 같고, 설치 디렉터리가 root 소유면 무엇을 해야 하는지 알려줌. snap이나 flatpak으로
설치한 VS Code는 **패치 자체가 불가능함** — 읽기 전용으로 마운트되기 때문임. `.deb`, `.rpm`,
타르볼을 쓰면 됨.

그 외 환경이거나 직접 하고 싶으면 같은 릴리스의 `.vsix`를 설치함.

```sh
code --install-extension neon-glow-<version>.vsix
```

또는 VS Code 안에서: 확장 뷰 → `...` 메뉴 → *VSIX에서 설치…*.

확장을 설치하는 것만으로는 아무것도 빛나지 않음. 페이로드는 `workbench.js`에 살고, 거기 넣는
것은 패치뿐임. 확장은 활성화될 때 패치되지 않은 번들을 알아채고 고칠지 물어봄. 팔레트에서
`Neon Glow: Show status`를 직접 실행해도 됨. 어느 쪽이든 쓰기 권한과
**완전 재시작**이 필요함. 일상적인 켜고 끄기는 둘 다 필요 없음.

마켓플레이스에는 없고, 앞으로도 올리지 않음. `workbench.js`를 다시 쓰는 확장이 심사를 정직하게
통과할 수는 없음.

### 클론해서

확장 폴더에 바로 클론한 뒤 리로드함.

```sh
# Windows
git clone https://github.com/Ruminem/vscode-neon-glow "%USERPROFILE%\.vscode\extensions\vscode-neon-glow"
# macOS / Linux
git clone https://github.com/Ruminem/vscode-neon-glow ~/.vscode/extensions/vscode-neon-glow
```

그다음 마찬가지로 `Neon Glow: Show status`를 실행함.

### 명령줄에서

확장 없이 번들만 직접 패치함.

```sh
git clone https://github.com/Ruminem/vscode-neon-glow
cd vscode-neon-glow
node install.js          # 되돌리려면  node uninstall.js
```

특정 설치를 지정하려면 `--target "<resources/app 경로>"`. 확장이 없으면 명령도 없으므로 토글은
`Ctrl+Alt+N` 폴백으로 떨어짐.

어느 경로든 끝나면: **VS Code를 완전히 종료했다가 다시 켬.**

### VSIX 직접 빌드하기

```sh
npm run package          # -> neon-glow-<version>.vsix
```

커밋에 `v<version>` 태그를 달면 CI가 빌드해서 GitHub 릴리스에 붙임. 태그와 `package.json`의
`version`이 다르면 잡이 실패함.

아이콘은 그린 것이 아니라 생성한 것임. 그래서 README가 인용하는 팔레트와 어긋나지 않음.

```sh
node tools/make-icon.js          # -> icon.png   (다른 형태: bars, n)
```

의존성은 없음. 형태는 signed distance field이고, 블룸은 확장이 실제로 칠하는 것과 같은 감쇠이며,
PNG는 `zlib` 위에 직접 조립함.

## 조정

설정(`Ctrl+,`)을 열고 `Neon Glow`를 검색함. 바꾸면 열려 있는 에디터에 1초 안팎으로 반영됨.
재패치도 재시작도 필요 없음.

| 설정 | 기본값 | |
|------|--------|--|
| `neonGlow.glowLayers` | `3` | 토큰당 후광 겹 수. 항상 도는 테두리 겹은 여기 안 들어감 — 비싼 쪽은 이것. 아래에 있음 |
| `neonGlow.maxBlur` | `36` | 블러 반경 하나의 상한. 기본값이 이미 최대치라 그대로면 변화 없음 |
| `neonGlow.brightness` | `1.0` | 전체 세기. `0`이면 색은 그대로 두고 글로우만 없앰 |
| `neonGlow.minChroma` | `0.30` | 이보다 밋밋한 색은 빛나지 않음 — 본문 텍스트를 걸러내는 것이 이 값임 |
| `neonGlow.chromaSpan` | `0.50` | 임계값 위로 크로마가 얼마나 더 있어야 최대 세기에 닿는가 |
| `neonGlow.floor` | `0.40` | `minChroma`를 겨우 넘긴 색의 세기 |
| `neonGlow.minLightness` | `0.25` | 아무리 채도가 높아도 이보다 어두우면 건너뜀 |
| `neonGlow.cursorTrail` | `0` | 커서가 새 위치로 미끄러지는 시간(ms). 커서 글로우가 꼬리를 남김. `0`이면 그대로 튐 |
| `neonGlow.saveShake` | `0` | 저장할 때 워크벤치가 흔들리는 폭(px). `0`이면 가만히 있음. `files.autoSave`를 쓰면 끄는 게 나음 |
| `neonGlow.findGlow` | `0` | 찾기 결과가 번지는 폭(px). 테마 자신의 찾기 색을 씀. `18`부터 시작해볼 만함 |
| `neonGlow.selectionGlow` | `0` | 선택 영역이 번지는 폭(px). 테마 자신의 선택 색을 씀. `12`부터 시작해볼 만함 |
| `neonGlow.occurrenceGlow` | `0` | 커서가 놓인 심볼이 화면에 나온 자리마다 번지는 폭(px). `10`부터 시작해볼 만함 |
| `neonGlow.gutterGlow` | `0` | 거터의 변경 막대가 번지는 폭(px). 테마 자신의 `editorGutter` 색을 씀. `8`부터 시작해볼 만함 |
| `neonGlow.caretArc` | `off` | 커서가 뛴 길에 무엇을 그릴지: `arc` `beam` `comet` `flash` |
| `neonGlow.caretArcMinJump` | `5` | 아크를 그리기까지 필요한 이동 거리(px). 한 글자보다 작아 화살표도 걸림 |

마지막 여섯 개는 `0`으로 나가고 값을 넣기 전까지 아무것도 하지 않음. 이미 돌고 있는
글로우를 조정하는 값이 아니라, 켜서 쓰는 새 동작임.
[토큰 말고 빛나는 것](#토큰-말고-빛나는-것)에 설명이 있음.

재시작이 필요 없는 이유는 이 값들이 패치 안에 살지 않기 때문임. 확장이 토글과 같은
`state.json`에 값을 쓰고, 렌더러가 다음 폴링 때 범위를 다듬어 적용하면서 테마의 토큰 색으로부터
스타일시트를 다시 만듦. 그래서 번들은 한 번만 쓰면 됨.

같은 값이 `neon-glow.js` 맨 위의 기본값이기도 함. CLI로만 설치한 경우 그쪽이 쓰임 — 거기엔
값을 보내줄 확장이 없음. 그것을 고쳤다면 `node install.js`를 다시 돌리고 재시작해야 함.

### 무엇이 비싼가

에디터는 가상화하므로 10,000줄 파일이 곧 10,000개의 빛나는 span은 아님. DOM에는 화면에 보이는
줄만 있음. 비용은 파일 크기가 아니라 **뷰포트 크기와 언어의 토큰 밀도**에 비례함.

그래도 실제 일임. `nlohmann/json`의 27,000줄짜리 단일 헤더에서 50줄이 보이는 화면 — 토큰 span
390개, 그중 빛나는 것 220개, 괄호 77개 — 을 놓고 실제로 스크롤을 구동하면서 컴포지터의
`RasterTask` 시간을 합산한 값:

| | 래스터 |
|---|--------|
| 글로우 없음 | 12 ms |
| `glowLayers` 2 | 16 ms |
| `glowLayers` 3 (기본) | **87 ms** |

가장 넓은 겹은 면적 산수가 예측하는 3분의 2가 아니라 **사실상 전부**임. 블러 시간이 반경보다
훨씬 빠르게 오르고, `36px`이면 이웃 토큰끼리 블러가 대량으로 겹침.

`maxBlur`는 같은 레버를 더 잘게 쓴 것임. 겹을 통째로 빼는 대신 반경에 상한을 둠. 아래는 별도
실행이라 같은 열 안에서만 비교 가능함:

| 상한 | 래스터 | |
|------|--------|--|
| `36` (기본) | 71 ms | 변화 없음 |
| `32` | 65 ms | −9% |
| `30` | 58 ms | −18% |
| `28` | 47 ms | −34% |
| `26` | 39 ms | −45% |

**두 표 모두 `0.9.9` 이전 감쇠 공식으로 잰 것이고, 지금 기준으로는 숫자가 높게 읽힘.**
그때 알파는 `2 / 5 / 16 / 36px` 위에 `0.95 / 0.75 / 0.65 / 0.40`이었고, 지금은
`1 / 5 / 11 / 26px` 위에 `1.00 / 0.65 / 0.32 / 0.14`임.

빠르게 하려고 바꾼 게 아니라 **더 잘 보이게 하려고** 바꾼 것임. 블러는 원본 자리에서 가장
진하므로 모든 겹이 글자 바로 옆에도 칠함. 옛 알파는 거기서 약 `2.75`로 더해졌는데,
`1.0`을 넘으면 다 같은 불투명이라 **가장 넓은 겹이 글자 가장자리에서 가장 좁은 겹만큼
진했음.** 그러면 눈이 경계를 찾을 기울기가 남지 않음. 글자 안쪽 구멍이 메워지고, 이웃한
번짐이 단어 사이 여백을 단어만큼 밝게 만들었음. 눈에 보이는 것은 총량이 아니라 **가장
안쪽 겹과 가장 바깥 겹의 비율**임.

넓은 두 반경을 좁힌 것이 그 변경에 딸려 왔고, 시간은 거기서 줄었음. 두 공식을 한 화면에
번갈아 적용하며 이웃한 쌍끼리 비교하는 `tools/bench.js`로 재보니 새 배분이 래스터 시간을
**57% 덜 씀** — 네 쌍이 각각 −56.3%, −57.3%, −56.8%, −57.4%였음. 위 표가 세운 순서는
그대로임. 겹 수와 반경이 여전히 비용이 있는 자리임.

`maxBlur`는 기본값에서 더는 아무것도 묶지 않음. 공식이 스스로 `26px`에서 멈추기 때문임.
`brightness`를 `1`보다 올리면 모든 반경이 같이 커지므로 그때는 의미가 있고, 공식보다 더
좁게 번짐을 자르고 싶은 사람에게도 의미가 있음.

`brightness`도 반경을 줄이긴 하지만 절반으로 낮춰야 3분의 1 정도임 — 좁은 두 겹은 거의 안
움직임 — 그래서 빨라지는 것보다 흐려지는 쪽이 훨씬 큼.

그 밖에는 움직인 것이 없음. SynthWave에서 물려받은 레이어 승격 꼼수인
`backface-visibility: hidden`을 떼어봤더니 노이즈 안이라 그대로 뒀음. 그리고 위 숫자들은 같은
변형을 바로 옆에 붙여 쌍으로 잴 때만 노이즈와 구분됨. 캐시가 데워지면서 래스터 시간이 계속
아래로 흐르기 때문임.

**밋밋한 테마는 다른 숫자가 필요함.** 기본값은 유난히 채도가 높은 Monokai에 맞춰져 있음. 예를
들어 Abyss는 그 절반 언저리가 상한임. 클래스 이름 색 `#ffeebb`는 크로마가 `0.27`이라 `0.30`
문턱에 아예 못 닿는데, 주석 색 `#384887`은 `0.31`로 통과함 — 빛나는 역할이 거의 뒤집힘.
`minChroma`를 `0.25` 언저리로 낮추고 `brightness`를 `1` 위로 올리면 되돌아옴.

## 발목 잡는 것들

**"창 다시 로드"로는 반영되지 않음.** 그건 소프트 리로드이고, Chromium은 `vscode-file` 번들을
캐시에서 내줌 — `vscode-file` 스킴이 `codeCache: true`로 등록돼 있기 때문임. 패치 이전에 뜬
창은 몇 번을 리로드하든 옛날 번들을 계속 돌림. 모든 VS Code 프로세스를 종료하고 다시 켜야 함.

**VS Code가 설치가 손상됐다고 경고함.** 예상된 동작임. `product.json`이 `workbench.js`의
SHA-256(base64, 패딩 제거)을 들고 있는데, 패치하면 그 값이 안 맞게 됨. 알림은 *다시 표시 안 함*
으로 닫으면 됨. `product.json`의 체크섬을 다시 써서 영구히 침묵시킬 수도 있지만, 그러면 이번
것만이 아니라 **앞으로의 모든** 변조 탐지가 꺼짐 — 알림 하나 때문에 치를 값은 아님.

**확장을 업데이트해도 패치는 그대로임.** 페이로드는 `workbench.js`에 살고, 새 VSIX를 설치해도
그 파일은 건드리지 않음. 그래서 새 릴리스가 렌더러에 추가한 것은 죽은 채로 남음 — 설정이
생겼는데 아무 일도 안 일어나는 식임. 주입된 배너가 페이로드의 해시를 함께 담고 있어서, 확장이
불일치를 알아채고 다시 패치할지 물어봄. 수락하면 다른 패치와 마찬가지로 완전 재시작이 필요함.

버전 번호가 아니라 페이로드의 해시인 것은 의도적임. 대부분의 릴리스는 확장만 바꾸는데, 버전을
찍어두면 이미 바이트 단위로 올바른 번들에 대해서까지 재패치와 재시작을 요구하게 됨.

**반대로 패치를 해도 확장은 갱신되지 않음.** 두 쪽은 서로 다른 명령으로 갱신되고 서로를
건드리지 않음 — `node install.js`는 `workbench.js`에 페이로드를 쓰고, VSIX 설치는 그
밖의 전부를 바꿈. **VS Code 설정 화면에 뜨는 설정 목록이 후자에 들어 있음.** 설정을
추가한 뒤 패치만 하면 페이로드는 그 값을 알아듣는데 설정 화면에는 항목이 없는 상태가 됨.
"설정이 안 먹는다"처럼 보이지만 사실은 항목 자체가 없는 것임. 설정에서 **Neon Glow**
옆의 개수를 보면 어느 쪽이 뒤처졌는지 제일 빨리 알 수 있음.

**VS Code 업데이트는 패치를 지움.** 업데이터가 `workbench.js`를 갈아끼움. 이건 확장을 갓
설치한 상태와 똑같은 상태 — 패치되지 않은 번들 — 이라서, 다음 실행 때 확장이 다시 패치할지
물어봄. `Neon Glow: Show status`를 직접 실행하거나, CLI로 갔다면
`node install.js`를 다시 돌려도 됨. 재설치는 안전함. 언제나 원본 `.pre-neon.bak`에서 다시
만들지, 이미 패치된 파일 위에 덧붙이지 않음.

일부러 번들을 원상복구하면 그 제안도 함께 꺼짐. 매번 닫아야 하는 알림으로 변하지 않도록.

**확장을 제거하면 번들도 원상복구됨.** `package.json`이 `vscode:uninstall` 훅을 선언하고,
VS Code가 확장을 제거할 때 그것을 node 스크립트로 실행함. 그래서 확장 뷰의 제거 버튼이
뒷정리까지 함. 다만 최선 노력임. 설치 디렉터리에 쓸 수 없으면 — 시스템 전역 설치인데 권한
상승이 없는 경우 — 훅이 실패하고 번들은 패치된 채로 남음. 그때는 권한을 갖춘 상태로
권한을 갖춘 상태로 `node uninstall.js`를 돌리면 됨. 확장을
*사용 안 함*으로 두는 것은 제거가 아님. 패치는 그대로 남고, 글로우는 마지막으로 본 상태로
계속 동작함.

**`files.autoSave`와 `saveShake`는 같이 쓰기 어려움.** 지연이든 포커스 전환이든 그것도
전부 저장이라 화면이 멈추지 않음. 흔들림은 기본이 꺼짐이라 켜야 겪는 일이지만, 켠 채로
자동 저장을 쓰면 1분 안에 다시 끄고 싶어짐.

**SynthWave '84와 나란히 둘 수는 있지만, 칠하는 것은 하나여야 함.** 저쪽은 `workbench.js`를
건드리지 않음. 그 옆에 `neondreams.js`를 쓰고 워크벤치 HTML에 `<script>` 태그를 넣음. 파일도
백업도 달라서 어느 쪽 패치도 상대를 망가뜨리거나 조용히 되돌리지 못함 — 함께 설치해도 안전함.
공유하는 것은 DOM임. 양쪽 다 `.vscode-tokens-styles`에서 `<style>`을 만들고 같은 특이도에
`!important`로 `text-shadow`를 걺. 그래서 나중에 붙은 쪽이 이기는데, 이건 규칙이 아니라 경합임.
SynthWave는 자기 테마가 활성일 때만 동작하므로 실제로 다투는 것은 그 테마를 쓸 때뿐이고 — 그때도
이 확장은 이미 그 테마의 색에서 글로우를 유도함. SynthWave의 패치가 하려는 일이 바로 그것임.

`Neon Glow: Show status`가 저쪽이 패치돼 있는지, 지금 실제로 다투고 있는지를 알려줌.
`Neon Glow: Disable`은 파일을 건드리지 않고 즉시 꺼지므로 둘 사이를 오가는 비용이 없음.

## 상태

**Windows 11의 VS Code 1.136.1**에서 개발하고 검증했음. 적용된 `text-shadow` 값을 Chrome DevTools
Protocol로 살아있는 렌더러에서 다시 읽어내 확인했고, 위의 래스터 측정도 같은 방식으로 했음.

| | 동작 | 검증 | |
|---|---|---|--|
| **Windows** | 됨 | 됨 | 사용자/시스템 설치 모두, 커밋 해시 resources 디렉터리 포함 |
| **macOS** | 될 것 | 안 됨 | 패치가 서명된 `.app` 내부 파일을 고치므로 **코드 서명이 깨짐**. 실제로는 계속 실행되지만 그게 거래 조건임 |
| **Linux**, `.deb` / `.rpm` / 타르볼 | 될 것 | 안 됨 | `/usr/share/code`는 root 소유라 팔레트 명령으로는 불가. `sudo node install.js` 또는 `sudo ./install.sh` |
| **Linux**, snap · flatpak | **안 됨** | — | 읽기 전용으로 마운트되어 무엇으로도 패치 불가. 확장이 그렇다고 알려줌 |

확장은 경로를 추측하지 않고 실행 중인 에디터에게 물어봄(`vscode.env.appRoot`). 그래서 포터블
빌드나 특이한 접두사도 모든 플랫폼에서 정확히 찾음. 추측이 필요한 것은 CLI뿐이고, 그때
`locate.js`의 목록을 씀.

macOS와 Linux는 동작하도록 작성했을 뿐 아무도 실행해보지 않았음 — 오작동하면 이슈를 열어주면
좋겠음.

## 출처

구문 강조가 빛날 수 있다는 것, 그리고 워크벤치를 패치하면 거기에 닿는다는 것 — 아이디어는
Robb Owen의 [SynthWave '84](https://github.com/robb0wen/synthwave-vscode)에서 왔음.
패치 방식은 다름. SynthWave는 워크벤치 옆에 스크립트를 떨구고 HTML에서 불러오지만, 이쪽은
`workbench.js`에 직접 덧붙임.
